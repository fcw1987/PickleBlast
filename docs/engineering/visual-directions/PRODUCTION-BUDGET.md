# Proposed production budget — not measured performance

These three images are art-direction concepts, not replacement screenshots, runtime textures, animation packs, or evidence of physical Watch performance. Choose one direction before full production. The Watch remains on build 6 during this review.

## First playable proof

Build only one player plus The Lobber in the selected direction, with the existing 271-frame / six-clip contract, source timing, contact frames, connected hand/paddle, foot anchor, alpha union and whole-frame registration verified. Prove a short idle/move/contact sequence before producing the complete animation set. Test the same contact and lob phases on the actual 40 mm viewport. The other four bosses follow only after the selected art and first playable proof are accepted.

Keep regulation court geometry and true-black playing surface generated by the engine. Do not import the complete concept screenshot as a background: image generation is not a geometry or exact-RGB guarantee. Bake environment material and localized lighting into separated original raster assets behind or outside the playing surface. Keep the lime ball and all shot/landing cues authoritative and above character artwork.

## Starting asset and rendering limits

These are proposed design limits, not a claim they are safe on Watch:

| Resource | Initial production target | Cost / reason |
| --- | --- | --- |
| Character frame size | Keep 128 × 128 runtime frames first | Existing visible player/boss footprints already resolve to roughly tens of display pixels. More source pixels cannot rescue a silhouette or detail that disappears at Watch scale. |
| Character lifecycle | Player plus selected boss; 271 frames per character, existing timeline | Preserve atlas release behavior, contact timing, and repeated-match memory bounds. |
| New source masters | Larger original masters allowed offline | Storage for working art is separate from decoded runtime texture memory. |
| Arena | One replacement 512 × 512 baked image, or equal decoded pixel budget split into layers | A single uncompressed RGBA 512-square image is 1 MiB before driver or mipmap overhead; replacing the existing image does not imply zero total rendering cost. |
| Extra localized effects | At most one optional 256 × 256 shared RGBA atlas | 0.25 MiB uncompressed pixel estimate; reuse existing effect pool and timing. No new particle system. |
| Extra scene nodes | At most eight beyond build 6 for the first proof | Reused nodes with no path rebuild each frame. Measure rather than infer safety from a small count. |
| Real-time post-processing | None | No fullscreen blur, bloom, dynamic lighting, shadow map, or extra compositing pass. Lighting is authored into the art. |

Doubling both runtime frame dimensions from 128 to 256 multiplies uncompressed pixels by four. Atlas trimming, compression, GPU allocation, caching and driver overhead affect the realized cost. Any resolution increase requires a same-device comparison; user tolerance for storage does not authorize unmeasured RAM/GPU growth.

## Acceptance measurements after selection

Compare baseline and candidate with the same signing/build configuration, Watch, OS, scene inputs and interruptions. Record displayed frame intervals against the requested 30 FPS (33.3 ms) cadence, long frames, startup/first-opponent load, resident-memory settling, twenty Home/rematch/opponent cycles, and sustained on-wrist warmth/battery observations. Record host CPU node-update timing and compiled atlas dimensions separately; neither substitutes for Watch frame pacing or GPU/memory behavior.

Retain exact core mechanics, Crown calibration/assistance, match rules, character timing, ball readability and contact registration tests. Inspect actual small/large simulator captures and on-wrist play. There is no production animation or physical performance result for these concepts yet.

## Dependency decision

Use the existing native SpriteKit/SwiftUI renderer and original pre-rendered artwork. None of the three styles needs a runtime graphics package. A package cannot supply the required authored silhouettes, equipment, source frames or contact registration. Offline authoring-tool selection and its licensing can be assessed when a direction is chosen; no third-party artwork or dependency has been added for this proposal.
